# Azure 在线客服低时延与后端切换方案

依据：《Azure客服模型调用说明.md》及本议题中的 body 超时、监控驱动切换要求。设计日期：2026-09-15。

## 1. 结论与推荐路径

建议采用 **“业务总截止时间 + APIM 健康后端路由 + 监控自动摘除慢后端”** 作为基础方案。若还要求同一次调用在 body 读取超时后尝试备用 endpoint，再增加 **完整响应执行器**，由它控制读取和缓冲，APIM 仍是唯一的模型区域选择方。

这两个目标需要分开验收：

| 目标 | 实现方式 | 能力边界 |
|---|---|---|
| 知识库不超过约 8 秒、整轮不超过 15 秒 | Java 编排与服务内部的端到端 deadline、取消和明确降级 | 保证及时结束等待，不等于每次都能拿到成功生成结果 |
| 避免新请求继续打到慢区域 | APIM 后端隔离、容量准入、监控控制器摘除 | 有检测和配置传播延迟，不救回已挂起的请求 |
| 本次 body 超时后改投另一后端 | 完整响应执行器 + APIM 有预算的单次跨后端补救 | 仅在尚未提交响应且剩余预算足够时执行 |
| 各区域单次 completion 数秒内完成 | 模型参数、输入输出长度、部署容量、实测准入 | APIM 无法让本身需要较长时间的模型强行在数秒内成功 |

**不建议**把每个 chat 调用都设成 8 秒，再串行重试三个区域；也不建议依靠分钟级 Azure Monitor 告警实现单请求秒级故障切换。

当前没有生产遥测、APIM SKU、部署容量和实际参数，因此下文数值是待压测的初始设计值，不是 Azure 服务承诺或已部署配置。

| 文档约束 | 设计处理 |

| Java 先意图、后知识库，串行调用 | 保留，不默认改成并行 |

默认按非流式、有限长度 JSON 回答设计。原文没有说明是否使用 SSE；如果实际为 SSE，第 6 节的透明补救只适用于向下游输出之前，不能把两个模型生成的流直接拼接。

## 3. 时延预算：先解决多个“8 秒”叠加

### 3.1 整轮预算

| 阶段 | 初始预算上限 |
|---|---:|
| 意图服务，含自身模型调用与处理 | 5.5 s |
| 知识库服务，整段 | 8.0 s |
| 编排、服务间网络、结果封装 | 1.0 s |
| 整轮最终保护余量 | 0.5 s |
| 总计 | 15.0 s |

Java 从接到请求时建立唯一的整轮截止时间；正常路径和降级结果尽量在 14.5 秒内完成。若意图或网络已消耗过多，知识库必须使用剩余时间，而不是再获得完整 8 秒。

### 3.2 知识库内部初始预算

| 阶段 | 阶段上限，包含该阶段所有尝试和开销 | 正常路径优化目标，待测 |
|---|---:|---|
| 查询改写 | 1.2 s | 短输出，P95 尽量低于 1 s |
| 在线 embedding | 0.5 s | 命中缓存或低时延部署 |
| Azure AI Search | 0.6 s | 限定 top-k、字段和查询复杂度 |
| 回答生成 | 4.0 s | 完整结果 P95 争取不超过约 3.2 s |
| 服务内部处理及尚未计入的网络开销 | 0.7 s | 分布式追踪定位 |
| 降级与结果封装预留 | 0.5 s | 不再调用模型 |
| 小计 | 7.5 s | 另留 0.5 s 至 8 s 硬截止 |

这是分配方案，不是实测结果。尤其改写和 embedding 的目标可能需要优化才能达到。阶段提前结束可释放余量，但不能侵占下游最低执行和降级预算；一期采用固定上限更容易控制，后续才考虑受限的动态借用。

**“两次 completion 各 P95 为 4 秒”不足以证明知识库 P95 ≤8 秒**：还有检索和网络，而且分位数不能直接相加得出整条链路的分位数。最终必须按完整用户回合统计。

### 3.3 Deadline 契约

服务内部统一使用：

```text
阶段有效预算 =
  min(阶段配置上限,
      整轮剩余时间 - 后续必需工作预留,
      知识库剩余时间 - 后续知识库工作预留)
```

没有足够预算就降级，不启动注定超时的调用。HTTP 客户端必须既有 connect/read 超时，也有覆盖完整调用的总截止时间；单纯的 socket read timeout 不能防止“不断少量返回、永远不结束”。

跨服务传递内部 deadline 和 trace ID，接收方扣减传输/时钟误差保护余量，并在本地使用单调时钟计时。这是必要的应用改动，不是区域路由头；应用仍不知道后端列表。入口必须删除外部伪造的内部预算头，并对可信调用者的预算做上限约束。

Container Apps 超时参数通过环境变量和新 revision 发布，符合现有运维方式。取消时要终止 HTTP 读取、释放连接和并发许可，不能只是让 Future 超时而底层调用继续占资源；向上游取消不能保证模型侧立即停止计费。

## 4. APIM 路由：隔离慢后端，而不是平均摊流量

### 4.1 后端组织

以“业务类别 × 模型部署 × 资源/区域”为健康和容量管理单元，至少分开在线 chat、在线 embedding、邮件 chat/离线索引。不要因为同一资源的 chat 429 就无条件禁用独立健康的 embedding。

候选仍为 East US 2、Sweden Central、Canada East。East US 2 因与网关/知识库靠近可作为初始优先候选，但**正式优先级和权重必须依据从现有调用路径测出的完整响应时延与可承载容量**，不能仅按地理距离排序。

所有允许接在线流量的候选都应通过数秒级性能准入；不达标的区域从在线候选集合排除，而不是长期拿真实客服流量试错。备用区域保持少量代表性探测/预热，并计入 token 成本。

逻辑模型名继续保留 `gpt-5.1`。物理部署名不一致时由 APIM 做显式映射；各区域模型版本、API 版本、请求参数支持、内容过滤和权限须一致。Embedding 还需保持模型、维度与 Search 索引向量空间一致，不能随意换一个同维度但不同的模型。

### 4.2 原生池与自定义路由的边界

基础版使用 APIM 原生 backend pool，按容量配置权重并配置可恢复错误的 circuit breaker。原生优先级池只有在高优先级组全部因熔断不可用时才进入低优先级组；“慢但返回 200”不会因 Azure Monitor 时延升高而自动熔断。[1]

因此，慢后端摘除由控制器明确修改**在线可选成员集合**。彻底摘除时移除成员或修改显式允许列表，不把“低优先级”或不确定支持的“权重 0”当作禁用开关。原生熔断与人工禁用分别记录，避免恢复流程解除人工隔离。Consumption 层不支持后端熔断器，实施前必须确认 SKU。

如启用第 6 节的请求内跨区补救，则使用 APIM 显式候选选择逻辑，保存已尝试 backend ID，第二次严格排除第一次的后端。不能简单再次调用原生池并假定它一定选到不同区域。

## 5. 监控驱动切换：分钟级治理链路

```text
应用完整响应与阶段遥测 / APIM 日志 / Azure OpenAI 指标 / 主动探测
  -> Azure Monitor 告警
  -> Action Group -> Azure Function 路由控制器
  -> 持久化健康状态、校验备用容量
  -> APIM 管理 API 更新允许列表/池成员
  -> 确认实际流量分布与配置版本
```

控制器可同时接受定时探测结果；不在每个用户请求中查询 Azure Monitor 或调用管理 API。指标、日志入库、规则窗口和配置传播都存在延迟，不能承诺故障后 1 分钟内切完。

### 5.1 信号与归属

| 信号 | 作用与注意事项 |
|---|---|
| 应用端 `call_total_ms` | 从发起到完整 body 读取、解析完成；是用户实际调用时延的主指标 |
| 意图、改写、embedding、Search、生成及整轮耗时 | 识别究竟是模型还是检索拖慢，不能把 Search 变慢归因到 chat 区域 |
| APIM `BackendDuration`、`Duration` | 辅助定位；原生粒度 1 分钟，只有平均/最大/最小，无原生 P95 聚合 |
| `ApiManagementGatewayLogs` | 使用 BackendId/BackendUrl、CorrelationId、错误等关联候选；核验实际字段填充和重试记录粒度 |
| Azure OpenAI Time to Last Byte | 原生指标 `AzureOpenAITTLTInMS`，用于后端完整生成时间诊断；仍需与应用端完整读取时间区分 |
| Time to Response、Time Between Tokens | 分析首个响应块与生成速度，不用 TTFT 代替整段完成时间 |
| 请求/生成 token、429、利用率、并发 | 排除输入输出长度变化、容量不足导致的慢，而不是所有问题都换区域 |
| 主动探测 | 覆盖无流量、长挂起、被摘除区域的恢复判断；要真正读取完整 body |

APIM 时延指标没有 BackendId 维度，不能用一个混合 API 平均值直接决定禁用某个区域。[3] P95/P99 用逐请求日志或直方图计算，不对每分钟 P95 再求平均。按调用用途、token 长度桶、部署和缓存冷热分组；超时/取消单列并计入失败率，避免只统计成功请求得到“健康”的假象。

从应用到 APIM 的请求使用 trace ID；APIM 平台记录实际选区与每次 attempt。必要时仅向可信内部调用者返回选区标识供关联，外部响应删除。不得记录完整对话、密钥或敏感正文作为常规遥测。

### 5.2 初始决策规则

以下是控制器规则，不是 APIM 原生时延熔断参数：

| 状态变化 | 初始条件示例 | 行为 |
|---|---|---|
| Healthy -> Suspect | 同用途、相近 token 桶的完整耗时 P95 超过预算的 80%，连续 2 个非重叠 1 分钟窗口，每窗至少 100 次 | 告警并减少份额，检查容量与业务输入变化 |
| Suspect -> Quarantined | 超时/可恢复故障率 ≥5%，每窗至少 100 次且连续 2 窗；或独立探测连续 3 次超过该用途截止时间 | 确认备用健康和容量后摘除，隔离至少 5 分钟 |
| Quarantined -> Recovering | 主动探测连续 5 分钟满足正常时延目标、错误率和容量要求 | 小流量试探，例如 1% -> 5% -> 20% -> 正常份额 |
| Recovering -> Healthy | 每级获得足够样本且持续健康，最低观察时间满足配置 | 恢复至容量允许的权重 |
| 任意状态 -> ManualDisabled | 人工隔离/配置不合规 | 自动化不得恢复 |

阈值按业务流量标定；低流量不满足 100 样本时不能判为健康，使用实际有完成超时的探测补充。单次探测很短的 prompt 不足以证明真实长历史/回答的 P95，应结合固定代表性样本和实际流量。

取消失败调用之后，应用记录失败的时间，而不是等 Azure OpenAI 长请求最终结束后才计数。SSE 场景探测首 token、最长 token/事件停顿及业务最大持续时间，不把长会话本身视为故障。

控制器要有单写者/分布式锁、幂等事件、版本或 ETag 并发保护、变更审计、冷却期和可回滚的配置快照。执行身份仅能修改指定资源。控制器失败时保留最近有效配置并告警；遥测过期不触发回切，尤其不能以“主区无请求、告警消失”推断恢复。

如全部候选慢或备用容量不足，进入明确的服务降级/限流，不循环切换、不重新启用已知坏区冒充恢复。

## 6. 要救回“本次 body 超时”：增加完整响应执行器

### 6.1 为何不能只写 APIM policy

`forward-request timeout` 定义为等待响应头，`buffer-response="true"` 是 8 KB 分块缓冲，不是完整 body 缓冲；不能据此证明“body 停顿 1 秒后，APIM 会重新向 B 调用”。[2]

基础方案已经能让应用及时取消并降级、让后续请求避开慢区，但不包含本次 body 超时的透明跨区补救。若这项仍是硬需求，执行器是本方案的必需扩展，不以一段未验证的 APIM XML 替代。

### 6.2 保持 APIM 唯一选区的部署方式

```text
知识库 / 意图服务
  -> 同一 APIM 入口：鉴权、用途预算、选择区域、补救判定
       -> 执行器 A（绑定 Azure OpenAI 后端 A）
       -> 执行器 B（绑定 Azure OpenAI 后端 B）
       -> 执行器 C（绑定 Azure OpenAI 后端 C）
```

执行器可由一个高可用服务的不同受控逻辑入口实现，并不要求三个不同代码库。APIM 选择入口/固定目标；执行器只调用绑定的 Azure 资源，不自行选区，也不允许外部传入任意 URL。部署于网关邻近位置起步，至少多副本常驻、连接复用、并发/内存有上限，避免冷启动；地域部署根据额外 RTT 和可用性实测决定。

执行器必须：

1. 验证内部身份与剩余预算，先扣除返回开销，再为上游设置连接、响应头、body 无进展和总截止时间；所有内部 SDK 重试关闭。
2. 在完整、大小受限的响应读取并校验前，不向 APIM 提交成功响应头或部分正文。持续少量数据也不能重置总截止时间。
3. 读取失败则关闭读取、丢弃部分内容，返回小型受控错误：如 504 + `body_read_timeout`；连接失败区分为 `upstream_connect_failure`。APIM 从可信错误元数据而非任意客户端头识别原因。
4. 上游实际 400/401/403、内容过滤/拒答不转成可重试错误；执行器自身配置/鉴权错误单独告警，不能通过跨区域绕过。
5. 超时、断流、截断、超限和解析失败不伪装成 200；不返回 A 的半个 JSON 加 B 的内容。响应头重建时正确处理 Content-Length、编码及逐跳头。

APIM 对执行器的等待响应头上限略高于执行器单次执行预算，但低于调用阶段剩余时间并预留返回余量。执行器完成读取后仍可能发生执行器到应用之间的传输故障；客户端总 deadline 继续作为最后保护，不能承诺所有网络故障都透明补救。

### 6.3 补救规则：最多两个不同后端，不额外增加预算

默认改写不补救；意图和回答生成可启用一次跨后端补救，但需要满足：

```text
错误属于可恢复的网络/超时/429/5xx
AND 尚未向下游提交响应
AND 存在未尝试且健康、容量足够的后端
AND 剩余阶段预算 >= 备用后端该用途预计完成预算 + 返回保护余量
```

APIM 显式记录 attempted backend IDs；第一次 A，第二次只能 B 或 C。若使用 `forward-request` 收到执行器的 504，可用状态码条件重试；执行器连接自身失败的路径需另外验证网关错误处理，不能假设所有异常都成为可判定的 504。网关的错误处理不可靠时直接 fail-fast，不能进入无界补救。

示例：生成阶段总预算 4 秒。A 在 0.8 秒发生 body 停顿并返回受控失败，APIM/网络已耗 0.1 秒，B 预计需 2.5 秒，返回余量 0.2 秒，则可尝试 B。若 A 已用 3.5 秒，即使 B 健康也应立即降级，而不是再给 B 4 秒。

body 无进展阈值必须按该调用模式的正常间隔分布设置，不能把“模型尚未生成首个结果”统一当成异常。示例中的 0.8 秒是故障时刻，不是所有请求的默认超时阈值。

不默认对冲并发请求；这会放大 token 成本与容量压力。模型重发即使无业务写副作用，也可能重复计费、生成不同答案；只接纳一个完整有效结果。工具执行/订单写操作若未来引入，必须在业务层另做幂等。

### 6.4 如何区分用途，而不让业务选区

意图和知识库可以按可信应用身份或已有 API 操作识别；同一个知识库身份下的改写与生成，若当前都走同一路径，APIM 无法天然区分。

扩展时增加受认证的内部用途标识（rewrite/generate）和剩余 deadline，或使用同一 APIM 域名下的分用途操作；这需要小范围应用适配，**不是**不改代码即可获得精确预算。用途只影响预算和重试策略，不指定区域。禁止解析 prompt 文本猜用途，也不信任终端用户自报的用途。

## 7. 降级、模型性能和容量

### 7.1 降级优先于超时堆叠

| 失败位置 | 本轮行为 |
|---|---|
| 意图 | 返回经业务批准的通用知识检索路径或转人工，不猜测执行敏感业务 |
| 改写 | 使用原句，不再调用改写模型 |
| 在线 embedding | 若业务验证允许，降级为 Search 文本检索；否则明确检索失败。在线向量重试共享 0.5 秒预算，离线索引走独立预算 |
| Search | 返回知识服务不可用/转人工，不用模型无依据生成 FAQ 或商品承诺 |
| 回答生成 | 返回可靠检索片段/固定服务提示/转人工，并带内部降级原因；不得伪装成正常生成 |
| 所有区域不可用或预算耗尽 | 有界失败/业务降级，不无限排队 |
| 400/401/403 | 直接失败及配置告警，不切区 |

保留原有“改写失败用原句”；其他降级属于建议的业务行为变更，需要产品批准并用评测验证。

### 7.2 模型和 token 优化

意图输出限定为类别/结构化短结果；改写限定为检索查询；生成设置合理 `max_completion_tokens` 和简洁回答要求。固定系统提示利于 prompt cache，但切区后的冷缓存必须计入性能准入，不把缓存命中当正确性前提。

评估当前 `gpt-5.1` 版本/API 支持的低推理开销配置，适用于分类/改写；先核实支持参数并评测质量，不能盲目加入参数导致 400。输出 token 上限不等于毫秒 SLA，并须检测截断或空结果。长对话历史需要受控摘要/窗口策略时，视为业务改动，不能静默丢失上下文。

如果 gpt-5.1 在真实输入和目标并发下达不到上述预算，选项是：减少必需模型调用、以规则/缓存替代部分改写、经批准更换更快模型，或调整时延/回答长度要求。不能只靠路由承诺“每区都稳定 2–4 秒”。官方性能指导强调模型、输出 token、输入和负载共同影响时延。[5]

### 7.3 容量与隔离

每个用户回合通常产生 3 次 chat（意图+改写+生成），知识库另有在线 embedding。容量规划按各用途真实 RPM、输入/输出 token、并发、缓存冷启动以及补救额外请求计算，而不是把用户 QPS 当模型 QPS。

设在线峰值需求为 P；摘除最大承载区域后，剩余健康后端的实测可用容量必须仍覆盖 P 和预留余量，否则提前限流/降级。分别核算 RPM、TPM 和并发；增加配额不自动保证低时延。对于稳定负载评估 Provisioned 容量的成本收益，但不把 PTU 当作每次 2 秒承诺。

核实现有部署究竟为区域型、Data Zone 还是 Global 类型。资源所属区域不应未经核实就等同于实际推理位置或独立故障域；跨 Sweden/Canada/US 的数据处理须遵守客户数据边界。

在线/邮件部署隔离之外，还要核对共享资源配额、APIM 并发和 Search 是否仍会互相争用。

## 8. 实施阶段与验收

| 阶段 | 交付 | 责任主体 |
|---|---|---|
| 0：基线和边界 | SKU、每区物理部署/模型版本/类型/配额，代表性 token 分布、真实阶段链路、SSE 与否、现有 SDK/APIM 重试 | 平台 + 应用 |
| 1：先止住长等待 | 15/8 秒共享 deadline、分阶段上限、取消传播、改写降级、独立在线限流、后端性能准入 | Java/知识库团队 + APIM |
| 2：慢后端自动摘除 | 应用/后端关联遥测、主动探测、告警控制器、状态机、审计和回滚 | 平台/SRE |
| 3：本次 body 超时补救 | 完整响应执行器、可信用途/预算、APIM 显式最多两后端逻辑 | 平台 + 应用 |
| 4：质量与容量调优 | 参数和 token 优化、故障后剩余容量、正常与降级质量评测 | 模型/业务 + 平台 |

若“本次 body 超时也切换”是正式验收项，阶段 3 不可省略；阶段 1–2 是可先上线的保护，不应标记为完整实现该项。

### 验收矩阵

| 场景 | 必须观察到的行为 |
|---|---|
| 正常峰值、长/短历史、缓存冷热 | 完整成功回合的 P95/P99、知识库/整轮耗时分别统计，正常生成质量不下降 |
| A 40 秒不返回响应头 | 阶段 deadline 提前结束，不出现应用等待 40 秒 |
| A 先发 200 响应头，再卡 body | 执行器未下发成功响应；有足够预算才改投不同后端，否则及时降级 |
| A 持续滴流或输出无限延长 | 总截止时间生效，不能被 idle timeout 不断重置 |
| A 返回 429/500/503 | 无同部署指数退避；跨后端补救若开启，最多一次且不超原预算 |
| 400/401/403、内容过滤 | 不换区、不绕过策略 |
| 改写超时 | 使用原句，并给后续检索/生成留预算 |
| embedding/Search 慢 | 正确阶段降级，不误摘除健康 chat 区域 |
| 自动摘除、恢复和重复告警 | 新流量退出坏候选，配置版本可追踪，冷却期内不反复切换 |
| 无流量、遥测中断 | 不误判恢复；保持安全配置并告警 |
| 备用过载/全部后端不可用 | 快速限流/降级，不产生重试风暴 |
| 用户取消 | 应用/执行器停止等待，连接与并发许可释放 |

硬截止验收以调用方边界的实际观测为准，包含计时/调度/网络误差；预留提前终止余量，不宣称故障网络下能保证每个客户端都在精确的第 15 秒收到报文。

同时报告“完整成功率”“降级率”“失败率”“超时率”，不能靠大量快速降级伪造低延迟达标。成功率和降级率阈值原文未提供，上线前由业务确定；阶段时延目标也必须与回答质量、token 范围和峰值并发一起签订。

发布采用新 revision/API policy 版本和小流量放量；出现质量下降、失败率升高或资源占用异常时，回退到已知健康路由/应用 revision，但保留总 deadline 保护。控制器与部署流水线共用配置变更约束，避免互相覆盖。

## 9. 明确不覆盖的故障

当前 APIM 网关与知识库在 East US 2，Azure AI Search 也属于业务依赖。只把模型分散到三个区域，不构成整套客服系统的区域级容灾。若要防 East US 2 整体不可用，还需独立设计入口、第二套网关/应用、检索数据同步、认证和网络切换；不能把该工作隐含在模型后端切换内。

本次交付为方案设计，未访问或修改生产 Azure 配置。实施前必须完成阶段 0 的事实确认；这不影响现在确定上述架构与能力边界。
