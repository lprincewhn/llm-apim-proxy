# 对齐错误率阈值后的 Foundry 指标复测

**已按多个状态码指标时序计算错误率，完成一次真实 B 自动切换。**
本轮首个 404 到备用首个 200 为 **5 分 53.05 秒**。
同时对这批流量运行不执行切换的 A 日志影子告警，B 的真实告警记录比 A 早
**69.21 秒**。这是本轮结果，不是普遍性能结论或 SLA。

本报告是 SVHWB-124 用户要求“把阈值对齐再测试一次 B”的后续结果，
不使用上一轮“五分钟五次 404”作为对齐后的方案。
此前 [次数阈值实验](apim-vs-foundry-metrics-20260916.zh-CN.md) 保留为历史记录。

## 1. 这次对齐了什么

错误率可以通过多个指标时序计算。此次读取 Foundry 的
`AzureOpenAIRequests`，按 `StatusCode` 拆分计数，再按同一窗口相加：

```text
E = N404 + N429 + Σ N500..599
N = Σ N所有状态码 − N401 − N403
ErrorRatePct = 100 × E / N
触发条件 = N ≥ 5 且 ErrorRatePct ≥ 20%
```

与 A 对齐的是：**五分钟窗口、至少五个有效请求、20% 合计错误率、
404/429/5xx 纳入、401/403 从分母排除**。其他有效状态，例如 400，
仍进入分母但不进入错误分子。不能把各状态码的百分比取平均。
分母为零时错误率未定义且不满足切换条件；缺失/异常遥测不伪装成健康值。

本轮固定 East US 2 账户、`gpt-5.1`、`ApiName=OpenAI`，
只累计已配置的聊天/Responses 操作时序，排除 embeddings 等其他操作。
实际演练流量全部为原生部署聊天接口，`api-version=2024-10-21`；
故障注入仍是删除 East US 2 `gpt-5.1`，Sweden 为健康备用。
本轮只对齐并复测**错误规则**，没有做时延规则或 SSE 故障注入。

## 2. 计算与告警实现

本次链路是：

```text
Foundry 状态码指标时序
  → 前台实验采集器每约一分钟读取最近五分钟、计算 E/N
  → 临时 Application Insights 接收计算后的自定义指标
  → Azure Monitor 原生指标告警
  → 原 Action Group / Logic App
  → 两次备用直探、ETag 路由写入
  → 后续请求到 Sweden
```

采集器同时发布 `EligibleSamples`、`ErrorCount`、`ErrorRatePct`，
以及由同一快照计算的 `ViolationCount`：
`N≥5 且 E/N≥20%` 时为 1，否则为 0。
Azure Monitor 对这个派生信号使用 `Maximum≥1`、一分钟信号窗口、
一分钟评估频率。**原始统计已经覆盖五分钟，不再对五分钟错误率叠加
另一个五分钟样本窗口。**
这不是人工发送 Fired 事件；真实 Azure Monitor 告警调用原有 Action Group。

这轮新增了计算与派生指标入库阶段，不能称为 Foundry 原始指标直接告警。
当前执行身份没有 Foundry 资源自定义指标写入所需的数据面权限，
所以采用有权创建的独立、临时 Application Insights 资源接收聚合数字；
未给身份增加角色，未保存/提交 instrumentation key 或任何访问令牌。
告警读取 Azure Monitor 的自定义指标，不通过 KQL 查询 AppMetrics 日志。

采集器仅为本次前台实验运行，不是已经部署好的常驻生产服务。
目标采集周期 60 秒；实际 28 个快照之间最短 60.92 秒、中位数 61.44 秒、
最长 66.21 秒，因为采集器与测试请求串行执行。
B 使用 UTC 整分钟结束的五分钟源窗口，A 按其服务评估相位取窗口；
二者窗口长度和业务阈值相同，但并非每次窗口边界完全重合。
采集、计算、入库和原生指标评估的耗时均计入本轮 B，没有从结果中扣除。

## 3. 同一批流量的 A 影子对照

生产 A 的两条告警在 B 演练期间关闭，避免 A 抢先改变路由。
另建 A 错误影子规则，复用生产 KQL、窗口、评估频率和阈值，
**Action Group 列表为空**，只记录真实告警而不调用控制器。
影子规则仅额外限制 `TimeGenerated≥本次演练开始时间`，防止启动时回放旧实验。
首次故障发生时已距本次开始超过五分钟，这个下界不改变当时的五分钟人口。

初建的无下界影子规则曾回放 03:11–03:16 的旧窗口，
在 03:49 生成一条历史告警；它早于本轮首个错误，与本轮故障无关。
该规则已删除，并在本轮首个错误前换成带下界的
`svhwb124-apim-errors-aligned-shadow`。**旧回放告警不参与速度比较。**

## 6. 阈值相同，数据人口仍不完全相同

必须保留这个限制：**数学阈值已对齐，但 Foundry 指标并不等于 APIM
逐请求日志的一一映射。**

第一次达到 B 阈值的源窗口为 **03:52:00–03:57:00**：

| 数据源 | 200 | 404 | 有效样本 | 错误率 |
|---|---:|---:|---:|---:|
| Foundry 指标，当时实际读取 | 31 | 8 | 39 | **20.51%** |
| Foundry 指标，演练后重查同窗 | 31 | 8 | 39 | **20.51%** |
| APIM 日志，后查同窗 | 47 | 10 | 57 | **17.54%** |

不能把这些计数差异全部解释为临时入库延迟，后查 Foundry 同窗仍是 39。
具体统计差异原因本轮未确定，也没有通过填补分母、缩放计数或读取 APIM
日志来“修正”B 的指标结果。
因此，**69 秒优势可能同时包含数据人口/时间桶差异导致的阈值跨越差异，
不能全部归因于 Foundry 指标传输更快。**

告警颗粒度的主要区别没有改变：A 能按 APIM API、路径、方法和网关/后端
状态定位业务请求；B 的原始指标能按账户、部署、模型、操作、状态、流式类型
划分，但不能按 APIM API/订阅隔离直连调用，也无法看见所有网关侧失败。
这轮派生指标是固定 East US 2 的聚合健康信号，不比原始指标拥有更多业务维度。

## 7. 收尾、交付与结论

原生产控制器定义、两条 A 告警及 `switchEnabled=true` 已恢复；
East US 2 模型按原 `GlobalStandard`、容量 150、版本 `2025-11-13` 重建，
两地均通过真实双探测。当前 **Sweden 主、East US 2 备用启用，路由版本 21**。
临时 B 指标规则、A 影子规则和计算指标 Application Insights 资源均已删除；
已写入既有工作区的实验遥测按其保留策略自然过期。
没有保留后台采集器、没有新增 RBAC。

代码：`deployment/monitoring/aligned_metric_experiment.py`。
导入不调用 Azure，生成规则默认关闭，不接入默认生产部署。
完整快照、逐请求数据、真实告警、动作状态、删除活动记录、清理记录及
重新计算脚本随 SVHWB-124 本次评论附件交付；摘要和关键原始数据也在
`deployment/monitoring/experiments/20260916-aligned/`。

**结论：错误率可以通过多个状态码指标计算，本轮已做到阈值对齐并跑通闭环；
同流量影子对照下 B 告警早约 69 秒，完整切换为首错后约 5 分 53 秒。**
仍应把它当作一次实现级实测，不将阈值相同误写成数据人口相同，也不承诺
原生 Foundry 直告警、常驻生产部署、时延/SSE/容量或任意故障均具备相同性能。
