# APIM 日志与 Foundry 指标：A/B 故障切换实测

> 后续已按多个状态码指标计算错误率并对齐阈值，见
> [错误率对齐复测](apim-vs-foundry-aligned-20260916.zh-CN.md)。
> 下文保留的是较早的次数阈值实验，不代表只能用错误次数触发指标告警。

**B 已跑通真实自动切换，但本次不能证明 Foundry 指标告警比 APIM 日志告警更快。**
从首个 404 算，A 为 **7 分 25.77 秒**，B 为 **15 分 52.16 秒**；
从告警记录生成算，两者到备用首个成功响应分别为 **21.33 秒、19.20 秒**。
主要差异在故障出现、满足阈值和遥测告警阶段，而不是下游切换控制器。

日期：2026-09-16。A 引用 SVHWB-107 的 9 月 15 日至 16 日真实直连拓扑演练，
不是旧执行器的 09:17 演练；B 为本次 SVHWB-124 的完整轮次 R3。
所有时间为 UTC，全部为单轮观测，不是 SLA。

## 1. 测试配置与可比性

两轮都通过 APIM 持续请求，删除 East US 2 的 `gpt-5.1` 部署，
由 Sweden `gpt-5.1` 接管。East US 2 为 `GlobalStandard`、容量 150、
模型版本 `2025-11-13`；Sweden 保持容量 10。
完整 B 轮与 A 使用相同的部署路径、`api-version=2024-10-21`，
同样要求响应为 `OK`、正常结束，约每 5 秒请求一次。
B 的指标/管理面采集也会占用循环时间，实际发送时间见逐请求记录。

| 配置 | A：现行 APIM 日志告警 | B：本次原生 Foundry 指标告警 |
|---|---|---|
| 数据源 | `ApiManagementGatewayLogs` | Foundry 账户的 `AzureOpenAIRequests` |
| 规则类型 | `scheduledQueryRules`，KQL | `metricAlerts`，平台指标，不经 AzureMetrics 日志导出 |
| 窗口／评估频率 | 5 分钟／1 分钟 | 5 分钟／1 分钟 |
| 本次错误条件 | 404、429、5xx 合计错误率 ≥20%，至少 5 个有效样本 | 指定部署聊天操作的 **404 次数 ≥5** |
| 业务范围 | APIM API `llm`，POST，已配置原生聊天及 v1 chat/responses 路径 | 一个 Foundry 账户 + `ApiName=OpenAI` + `ModelDeploymentName=gpt-5.1` + `OperationName=chatcompletions_create` + `StatusCode=404` |
| 后续动作 | Action Group → Logic App → 两次备用直探 → ETag 路由写入 | 复用同一个 Action Group、Logic App、身份、探测及路由写入 |

**两套阈值不等价，不能把本次结果解释为只替换遥测数据源的严格对照。**
本次 B 针对删除部署引发的 404；没有声称覆盖 A 的合计错误率或时延规则。
普通原生静态指标条件没有直接实现这里跨状态码求和、除以有效请求数并附加
最小样本门槛的 KQL 表达式。内置可用率 `(总调用−5xx)/总调用` 也不能代替
包含 404、429 且排除 401/403 的自定义错误率。

B 期间两条 A 告警均暂停，避免 A 抢先切换。仅临时改造控制器的指标告警入口，
校验固定规则名、账户、指标及维度，将已归因账户映射到 `eastus2`。
探测、当前主判断、备用资格、十分钟冷却、告警新鲜度、串行执行和 ETag 保护未改。
没有伪造 Fired 事件，没有手动完成测量中的 East→Sweden 切换。

## 3. 速度对照：必须同时看三个起点

| 耗时口径 | A：APIM 日志 | B：Foundry 指标 |
|---|---:|---:|
| 删除成功 → 首个 404 | 18 分 49.89 秒 | 4 分 32.42 秒 |
| 首个 404 → 告警记录生成 | 7 分 04.44 秒 | 15 分 32.96 秒 |
| 首个 404 → 备用首个 200 | **7 分 25.77 秒** | **15 分 52.16 秒** |
| 删除成功 → 备用首个 200 | 26 分 15.66 秒 | 20 分 24.58 秒 |
| 告警记录生成 → 备用首个 200 | **21.33 秒** | **19.20 秒** |
| 路由写入完成 → 备用首个 200 | 13.08 秒 | 12.62 秒 |

B 的第一个 404 与第二个 404 相隔 **10 分 15.94 秒**，中间继续成功。
首个孤立错误不足以触发五分钟内五次错误，因此“15 分 52 秒”不是指标管道本身的延迟。
反过来，B 从删除开始的总耗时更短，也不能证明告警更快——删除到数据面故障的传播过程不同。
此前重复删除／恢复也意味着两轮不是独立、同时、同故障轨迹的随机对照。

本轮按客户端响应结束时间回算，B 的五分钟五次 404 首次达到于 **03:08:52.724**
（61 个请求、5 个错误），A 的 20% 首次达到于 **03:11:08.198**
（60 个请求、12 个错误）。这只说明阈值不同，**不是 A 在 B 期间实际触发过告警**；
A 当时关闭，不能据此补造它的告警时间。

B 真实告警载明：窗口 **03:05:20.443–03:10:20.443**，`metricValue=7`，阈值 5。
窗口结束到告警记录生成约 **134.28 秒**，说明原生指标也不是零延迟。
客户端、指标桶和告警记录使用不同口径；不能将这一差值全部归为网络传输或指标入库。
表中“告警时间”统一取 Alerts Management 的 `essentials.startDateTime`；
B 的内部条件时间 `03:12:20.459` 不与 A 的告警记录时间混用。
写路由后到客户端成功还包含网关传播、请求采样间隔及请求耗时，不是纯传播延迟。

## 4. 告警颗粒度对照

| 维度 | A：APIM 日志 | B：Foundry 原生指标 |
|---|---|---|
| 时间颗粒度 | 单请求原始记录，可保留细粒度时间；当前规则仍每分钟评估五分钟窗口 | 实际账户指标最小桶为 **1 分钟**；不等于一分钟内必定告警 |
| 业务／入口归因 | 可用 API、完整后端路径、HTTP 方法、网关与后端状态等字段；当前查询精确限制推理路径 | 原生维度包括账户、部署、模型/版本、操作、状态码、区域、流式类型等；没有 APIM `ApiId`、订阅或任意 URL 路径维度 |
| 调用方隔离 | 只看该 APIM、该 API 的请求 | 同账户/部署的直连、Studio、健康探测等也可能计入，不能自动当作 APIM 专属请求数 |
| 故障覆盖 | 能同时看到网关与后端状态，部分后端未收到的请求可经网关错误计入；仍受现有路径归因限制 | 适合 Foundry 已收到、且服务确实产出指标的失败；看不到只发生在 APIM 前端或网关到上游网络上的全部失败 |
| 模型层诊断 | 当前为 `BackendTime` 和 HTTP 错误，不能由此拆出模型首 token/逐 token 时间 | 有响应时间、首 token、token 间隔、最后字节等模型指标，但须选对指标的适用范围与归一化定义 |
| SSE | 现有规则没有完整流中断／idle SLA 保证 | `StreamType` 及 token 时延可辅助定位；一分钟聚合也不是逐连接 idle 检测或断流恢复 |
| 复杂条件 | KQL 可做合计错误率、最小样本、排除条件、精确业务路径组合 | 固定指标维度的阈值告警更直接，但不能把不同状态码序列或不同流式指标随意当成同一错误率/时延 |

实际资源的维度目录已保存在证据中。模型维度更丰富，不意味着业务隔离更细；
两者是不同方向的颗粒度。

## 6. 收尾与建议

本次已恢复原始生产控制器定义、两条 A 告警及 `switchEnabled=true`。
临时 B 规则均已删除，没有长期同时运行两套切换来源。
East US 2 部署按原型号、版本、SKU、容量 150 恢复，两地均通过真实双探测。
当前 **Sweden 主、East US 2 备用已启用，路由版本 18**，不回切 East US 2。

建议继续保留 **A 作为 APIM 业务入口故障的主判断来源，B 作为部署／模型层的补充监控**。
本次证明 B 能走通同一自动切换链路，但没有证明替换 A 能缩短故障恢复时间。
若要据此做替换决策，应先统一错误人口、比例阈值和样本门槛，再对同一故障流量进行
两路只读影子评估，控制器只接受一个来源，分别量出“达到阈值→告警到达”的分布。
本次未验证 B 的 429/5xx、模型时延、SSE 中断或 N-1 容量，不能外推这些能力。
